About policy inputs and evaluation scope+

The current model comparison uses privileged assisted skill planning: structured simulator state and reference goals are supplied to a model, whose chosen skills are executed by IK/RRT and native controllers. A separate sensor-policy interface accepts actual RGB and measured robot joints.

Persona cases are authored configurations, local to each task. Default comparison seeds are development layouts. Automatic scores do not include visual review; task-specific validation limits remain documented in the repository.

01 / Data construction

Reconstruct what is missing.
Keep the annotations we already have.

“Video → Isaac” is a pipeline with distinct motion, scene and control stages. Released 3D annotations can bypass video reconstruction.

Existing ingestion / adapter componentsScene and interaction work varies by sampleLearned style conditioning is a development plan
01 — RECOVER & ALIGN

Motion and scene evidence

Check the clip, identity and action label. Reuse released motion; otherwise estimate visible body, hands and relevant objects. Align time, scale, camera and world coordinates.

02 — COMPLETE & RETARGET

A functional task scene

Add required supports, object articulation, collision geometry and robot controllers. Retarget with joint and morphology limits. Mark inferred or authored surfaces explicitly.

03 — REPAIR & VALIDATE

Close concrete failure cases

Inspect overlays and replay, repair bad fits or contacts, and rerun checks. Keep before/after evidence. Freeze task and persona criteria before the final policy evaluation.

Background ≠ interactive environment. A rendered backdrop or completed image cannot support a robot. Tables, containers and tools need geometry and physics. Unseen regions remain model-inferred or benchmark-authored rather than recovered ground truth.

03 / Persona representation

Build the profile from evidence.

Use released, participant-mapped attributes and independent user history. An identity key retrieves evidence; it does not imply personality, preferences or a particular correct action.

A compact subset of the released profile, not an invented persona. A handedness value or expertise score does not automatically specify the only valid execution. Released profile mapping ↗

1. Preserve explicit attributes

Original ID, released values, units, missing fields and per-field provenance. Keep action/session conditions separate.

2. Select independent history

Exclude the evaluation clip, duplicate or overlapping recordings, and—when testing cross-action transfer—the held-out action.

PLANNED3. Learn a style representation

Encode permitted history into zstyle. Test whether it captures stable behavior rather than camera, website or clothing cues.

4. Condition action selection

User evidence + instruction + current scene/robot observations → actions under the declared task contract.

Explicit profile xu+History / zstyle+Task + observations→Policy π→Robot actions

Observed, inferred, authored

Explicit persona: released participant-level data.
Latent style: estimated from independent history.
Authored persona: a separately labelled benchmark condition.

Population-only statistics stay population-only. Missing traits remain missing.

Support is not the answer

Held-out target motion, solution waypoints and success annotations stay on the evaluator side. Cross-action tests ask whether prior actions help with a new action.

Use matched scene, instruction and seed for persona counterfactuals. Changed output only counts when it satisfies the corresponding constraints.

04 / Evaluation

Score the task and the persona.

After construction, the agent must produce and execute its own actions. Recorded human motion and reference replay provide evidence; they are not policy trials.

Primary · personalized goal-state task success

Semantic task successANDApplicable persona constraints=Personalized success

Both components require declared verifiers and observed execution evidence. Include physical validity wherever the task contract requires it, and retain its diagnostics separately.

01

Condition the agent

Released profile or permitted history, task instruction and current observations.

02

Execute in Isaac

Model-selected actions through the supported robot controller; log actual states and outputs.

03

Run declared checks

Task goals, persona constraints and relevant physical observations; scoped semantic judging when needed.

04

Report with coverage

Success rates over valid, evaluated policy trials. Show missing evidence and failure reasons.

Executable task / persona criteria

Use measurable contracts.

Check an object state, goal region, required hand, motion sequence or other justified constraint. Attribute-to-constraint rules need independent support; they are not inferred from a demographic label or one demonstration.

Missing required criteria or observations → NOT_EVALUATED. For how to do it, an absent persona checker cannot be replaced with N/A. An extra execution-style check may be inapplicable to a persona-dependent goal task, with an explicit reason.

VLM semantic proxy · scoped pilot

Judge meaning against a rubric.

For signing, use a frozen, robot-aware semantic rubric and frame/video evidence. Return PASS / FAIL / UNCERTAIN with reasons. Accept embodiment differences that preserve the intended sign.

Calibrate against human clips, reconstructed references, wrong-sign and no-motion controls. The current YES-sign pilot is not validation of every gloss or of persona fidelity.

Primary outcome

Personalized task success: verified semantic task completion and applicable persona requirements. Also show task-only success and evaluated coverage.

Semantic evidence

A calibrated VLM judgment is an explicitly labelled semantic proxy where used. It does not replace contact measurements or establish expert-certified sign correctness.

Auxiliary diagnostics

ADE/FDE, motion similarity, smoothness, contact errors and retrieval scores explain behavior. Before comparing trajectories, fix compatible coordinates, timing, units and valid-joint masks.

Replace “VLM error(gt_action, pred_action)” with “evaluate(task, persona, executed behavior, rubric).” A human demonstration is one reference behavior, not necessarily the only correct solution. Similar motion can still perform the wrong sign or miss the task goal.

05 / Persona development plan

From preserved information
to verified personalization.

Keep current infrastructure separate from the experiments needed to establish a useful user representation.

PHASE 01

Existing schema & conditioning

Preserve user evidence

Map released attributes to users, retain provenance and missingness, and construct leakage-safe support sets.

PHASE 02

Task-specific work

Define valid alternatives

Choose comparable tasks and independently justify persona constraints. Finish assets and executable checkers; freeze them before final evaluation.

PHASE 03

Proposed experiment

Learn persistent style

Compare explicit profile, history-only and combined inputs. Test cross-action transfer and isolate recording-condition shortcuts.

PHASE 04

Proposed validation

Test conditioning benefits

Hold scene, instruction and seed fixed; swap the supported persona. Compare with no-profile and shuffled-profile controls using the frozen criteria.

Research scope

We transform real-human demonstrations and available user information into persona-conditioned robot tasks. Depending on the dataset, we reconstruct motion from video or reuse released 3D annotations, retarget the motion, and complete the required Isaac scene and controllers. Policies receive a grounded user representation, task and observations. The primary outcome is task success together with verified persona constraints; VLM semantic judgments and trajectory errors provide separately reported supporting evidence.
